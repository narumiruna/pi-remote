## Feedback items

### R1 — Stop confirmation can affect a later run

- Source: https://github.com/narumiruna/pi-remote/pull/6#discussion_r4302817702
- Scope: in scope. The PR introduces Stop and Close confirmation.
- Severity: P1. An old confirmation can abort new accepted work without a new decision.
- Evidence: `SessionContext` contains only host, epoch and session ID. `closeSession` captures the current working snapshot after confirmation. The same session can finish and accept another prompt without changing that context. Later phase checks cannot distinguish these runs.
- Outcome: Already addressed in published fix `c4b083c`.
- Change: `prepareSessionClose` captures an opaque `LocalCloseConfirmation` before presenting the dialog. The host checks lifecycle/work identity before a new journal entry and mutation reservation. Work dispatch and run boundaries change the work generation; ordinary message completion does not. Pending dialogs and mutations reject consent. The wire format and original `handle` signature remain unchanged.
- Evidence: host tests cover accepted work before run events, pending dispatch, coalesced run boundaries, ordinary output and pending dialogs. The paired Mac-model test and native confirmation test reject newer same-session work. All checks below pass.
- Reply: https://github.com/narumiruna/pi-remote/pull/6#discussion_r4302909449
- Thread: resolved through `resolveReviewThread`; the API returned `isResolved: true`.

### R2 — A same-ID reactivation can be hidden

- Source: https://github.com/narumiruna/pi-remote/pull/6#discussion_r4302817704
- Scope: in scope. The PR adds local closed-session visibility after host close.
- Severity: P2. Active work can disappear from the sidebar and remain recorded as closed.
- Evidence: the post-close guard accepts `state.selected == id` without comparing snapshot order. This accepts both stale pre-close state and a newer same-ID activation. The observer does not remove closed IDs when a session is activated remotely.
- Outcome: Already addressed in published fix `c4b083c`.
- Change: synchronous `finishSessionClose` rejects a newer same-ID activation before saving visibility. Later authoritative activation removes the closed ID and reveals the workspace. In-memory receipt watermarks distinguish delayed pre-close snapshots from later activation, including a new host epoch.
- Evidence: `testCloseReceiptRejectsAnAlreadyObservedSameSessionReactivation` and `testLaterActivationRevealsClosedSessionButStaleSnapshotsDoNot` pass. They cover both observer orderings and check preserved catalog, workspace and draft data.
- Reply: https://github.com/narumiruna/pi-remote/pull/6#discussion_r4302909650
- Thread: resolved through `resolveReviewThread`; the API returned `isResolved: true`.

### R3 — Confirmed Stop must preserve request deduplication

- Source: independent review of the R1 fix.
- Scope: in scope. The new consent check must not change existing request replay rules.
- Severity: P2. A completed Stop must return its recorded result; an unfinished duplicate must report an unknown outcome without another dispatch.
- Evidence: checking the work token before the journal rejects the original token after Stop changes the work generation. This returns conflict before reading the accepted request's record.
- Outcome: Already addressed in published fix `c4b083c`.
- Change: a value-copy journal probe returns completed or in-flight outcomes before consent validation. New, stale attempts do not enter the real journal. The existing path for requests without a confirmation remains unchanged.
- Evidence: `closeConfirmationReplaysPendingAndCompletedStopWithoutDispatch` passes. It verifies unknown outcome during Stop, recorded success after completion and exactly one abort. `closeConfirmationRejectsAcceptedWorkBeforeAnyRunEvent` verifies that a stale, undispatched attempt does not reserve its request ID.
